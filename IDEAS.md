# Идеи для масштабирования приложения

Список задумок на будущее — не в работе прямо сейчас, фиксируем, чтобы не забыть.

## 1. Раскрывающийся список товаров (группы, категории)
В экране менеджера (заказ на витрину) список товаров сделать сворачиваемым по категориям —
аккордеон вместо (или в дополнение к) плоского списка/вкладок-фильтров. Актуально, когда
товаров становится много и плоский список неудобно листать.

## 2. Автоматическое напоминание о дедлайне подачи заявки
Дедлайн 10:30 сейчас просто отображается в шапке — напоминание отстающим точкам шлёт вручную
управляющий кнопкой «Напомнить отстающим». Механизм push-уведомлений в Телеграм уже есть
(сделан для заявок на регистрацию, `src/lib/telegramNotify.ts`) — можно повесить
автоматическую задачу (Vercel Cron) рядом с дедлайном, которая сама разошлёт push всем точкам
без поданной заявки, без участия человека.

## 3. Реальная Telegram-идентификация для Управляющего/Территориального/Менеджера
Сейчас так по-настоящему устроен только вход Владельца (проверка подписи Telegram `initData`).
Управляющий — общий ПИН, территориальный — выбор из списка, менеджер — просто устройство
(localStorage). Правильное решение — распространить тот же механизм verifyTelegramInitData
на остальные роли, с привязкой Telegram id к записи в `staff`.

## 4. Довести права территориального управляющего до реального действия
Матрица прав (Владелец → «Роли и права») уже хранит, что разрешено территориальному
управляющему, но `TerritorialManagerView.tsx` сегодня полностью read-only — там нет ни одной
кнопки действия, чтобы это применить. Нужно прокинуть нужные обработчики (принять/отклонить
заявку, напоминания и т.д.) в этот экран и показывать их по матрице прав.

## 6. Понятная ошибка при сбое отправки заявки — ✅ сделано 14.09.2026
Оказалось хуже, чем «ошибка видна только в консоли». Ответ сервера **вообще не проверялся** —
ловился лишь обрыв соединения, поэтому ошибка, которой сервер отвечал, читалась как успех.
А сообщение «заявка успешно отправлена» показывалось **до отправки запроса**. Вместе:
менеджер видел зелёное «отправлено», закрывал приложение, а заявки в производстве не было.

Сделано:
- ответ сервера проверяется, а не только обрыв связи;
- «отправлена» показывается только после подтверждения от сервера;
- при сбое — красная плашка, которая не исчезает, с кнопкой «Повторить»; набранное остаётся;
- оптимистичный статус откатывается обратно в «Черновик», чтобы экран не утверждал, что
  заявка подана, когда на сервере её нет;
- одна тихая повторная попытка через 2 секунды, чтобы секундный провал связи не пугал людей.

## 7. Отдельная тестовая база Supabase для локальной разработки
Локальный `npm run dev` сейчас использует ту же боевую базу, что и продакшн. 13.09.2026 это
обошлось дорого: фоновая проверка «исчезла ли операция `simulate-all`» раз в 10 секунд слала

реальных заявок не было; утром это стёрло бы рабочий день всей сети. Всё поддельное удалено,
но причина осталась: одна база на разработку и на продакшн.

## 10. Дашборды на основе API iiko
Начать интеграцию с API iiko (Айко) — раздел с дашбордами, подтянутыми оттуда, с сравнением

доступны через API iiko и что конкретно сравнивать (выручка, списания, продажи по товарам и т.д.).

## 11. Красивые ТКК с картинками слоёв продукта
Технологическая карта блюда сейчас — просто таблица (название/количество/цена). Сделать
визуальное представление в стиле реальных ТКК — с картинкой в разрезе, показывающей слои
состава (как физически собирается блюдо), а не только текстовый список ингредиентов.

## 12. Клик по продукту у внутреннего сотрудника открывает его ТКК

техкарту (состав, технология), чтобы можно было свериться с рецептурой на месте, не отвлекая
управляющего.

## 13. Приёмка на точке
Сейчас в системе есть только «что заказали» — что реально доехало до точки, нигде не
фиксируется. Менеджер после доставки отмечает фактически принятое количество, и расхождение
«заказано → принято» сразу видно управляющему: это либо недовоз из цеха, либо потери по
дороге, и сегодня ни то, ни другое не отслеживается никак.

Экран переиспользуется почти целиком — тот же список товаров, что и в заявке, но со второй
колонкой факта. В базе нужно место под принятое количество (отдельное поле на строке заказа
либо отдельная сущность приёмки с привязкой к дате и точке).

Это первый из трёх шагов, замыкающих круг «заказ → производство → чек-лист → **приёмка** →
остатки и списания → норма на завтра». Без него следующие два повисают в воздухе.

## 14. Журнал действий
Сегодня нельзя ответить на вопрос «кто удалил эту заявку и когда» — никаких следов не
остаётся вообще. Нужна простая таблица «кто, что, когда, над чем»: приём и отклонение
заявок, удаление заявок, одобрение регистраций, правки каталога и цен.

Особенно нужен после того, как появятся права по должностям: без журнала выданные права
невозможно проверить — видно только то, что кнопка есть или её нет, но не то, кто чем
воспользовался.

## 15. Комментарий к заявке
Поле для заметки у заявки **уже есть в базе** (`notes` в таблице `orders` и в типе
`ShopOrder`), но в интерфейсе его нет нигде — ни при подаче, ни в реестре у управляющего.
«Завтра мероприятие, нужно больше обычного» сейчас передать некуда, кроме звонка.

Самый дешёвый пункт из всего списка: нужно только поле ввода на экране заявки и показ этого
текста в реестре.

## 16. Оповещения управляющим производством
Разослать решение по заявке (принята/отклонена) умеет всем троим — подавшему, владельцу и
управляющим производством. Но список получателей для последних (`ADMIN_NOTIFY_TELEGRAM_IDS`)
**пустой**, поэтому им не приходит ничего: ни о новых заявках на регистрацию, ни о решениях
по заявкам точек.

Это не задача на код — нужно добавить их Telegram-номера в настройки на сервере (и локально,
и в Vercel). Пока они не заданы, уже написанная половина работы по оповещениям простаивает.

## 17. Кабинет владельца точки
Сегодня в системе четыре роли: Владелец (сеть целиком), Управляющий/Админ (производство),
Территориальный (до 5 точек), Менеджер точки (одна точка, только заказ). Нужен ещё один
кабинет — для владельца конкретной точки: не сотрудник, а тот, кому эта точка принадлежит.

Не уточнено, что именно он должен видеть и что мочь — например, свою выручку/заявки/приёмку
только по своей точке (read-only, как у территориального, но на одну точку) или что-то шире.
Уточнить у владельца сети при выборе этой идеи в работу.

## 18. Два разных названия одной и той же роли
При регистрации внутренний сотрудник выбирает должность **«Заведующий производством»**.
После одобрения он попадает на экран, который называется **«Управляющий производством»**
(и так же подписан в переключателе «Смотреть как» у владельца). Нигде не сказано, что это
одно и то же — со стороны выглядит как два разных человека/роли. Стоит либо привести к одному
названию везде (в должности, в заголовке экрана, в переключателе), либо явно пояснить связь
на экране регистрации («станет управляющим производством»).

## 19. Просмотр «Сотрудник цеха» у владельца путает управляющих с рядовыми
Проверил на реальных данных: если владелец открывает «Смотреть как» → «Сотрудник цеха» и
выбирает Адиля (его настоящая должность — «Заведующий производством»), экран показывает
обычный табель — «Отработано 0 смен, Заработано 0 ₸», как у рядового пекаря. Но на СВОЁМ
устройстве Адиль давно открывает не табель, а полноценный кабинет управления цехом. Превью
владельца врёт о том, что видит человек на самом деле. Список для этого превью стоит либо
исключить из него людей с должностью «Заведующий производством», либо переключать превью на
кабинет управления для них.

## 20. Заведующий производством — в общем табеле наравне с пекарями
Сейчас и Адиль, и Адил (оба «Заведующий производством») висят в списке табеля с чекбоксами
«отметьте смену» и ставкой за смену, как любой пекарь или заготовщик. Не уверен, что это
осознанно: если управляющий производством — не сменный рабочий, а руководитель на окладе,
ему, вероятно, не место в этом списке вовсе. Если это осознанно (человек и руководит, и
иногда встаёт к тесту) — тогда всё как есть, просто стоит подтвердить.

## 21. Оповещение «Аванс отклонён» не говорит, о какой сумме речь
Одобрение показывает сумму («20 000 ₸ переведут на Kaspi …»), а отклонение — нет, только
«Уточните детали у управляющего». Если у человека когда-нибудь окажется больше одной
отклонённой заявки за месяц, он не поймёт, о какой из них сообщение. Стоит добавить сумму и
туда же, для симметрии.

## 22. Оповещения открывают приложение, но не туда, где нужно
Каждое Telegram-сообщение (новая заявка, авaнс, дедлайн) несёт кнопку «Открыть приложение» —
она всегда ведёт на самый верхний экран, а дальше человек сам ищет нужный раздел (Реестр
заявок, Авансы, Персонал). У Telegram Mini Apps есть механизм диплинков через `start_param` —
можно передавать, какой именно экран открыть по нажатию на конкретное уведомление. Не
маленькая правка (нужен роутинг по параметру при старте), но ощутимо ускорит реакцию
управляющих на реальные события.

## 23. Бейдж территориального в шапке на телефоне — без имени
У территориального управляющего в шапке справа есть значок (компас в кружке) — на мобильной
ширине имя рядом с ним скрыто классом `hidden sm:inline`, остаётся один значок без подписи.
Не критично, но не несёт пользы в таком виде — или убрать совсем на мобильном, или оставить
короткую подпись.

## 24. Поиск и фильтры в «Персонале» видит только вкладку «Сотрудники»
Вчерашний редизайн добавил поиск по имени/телефону и три фильтра, но только для списка уже
принятых сотрудников. Вкладка «Заявки на регистрацию» остаётся как раньше — простой список без
поиска. Не мешает при паре заявок, но при всплеске регистраций (как было 17.09, четырнадцать
заявок за час) пролистывать длинный список неудобно ровно там, где решение нужно быстрее всего.

## 25. Мелочи, не тянущие на отдельную задачу
- Текст «Регистрация подтверждена»: «...приложение уже открыто для вас. Откройте его и
  начинайте работать» — сам себе противоречит («уже открыто», затем «откройте»). Можно
  переписать проще: «...заявка одобрена. Откройте приложение и начинайте работать».
- В сетке «Управление цехом» семь плиток на два столбца — последняя («Роли и права») висит
  одна в своей строке. Чисто внешне, ни на что не влияет.
