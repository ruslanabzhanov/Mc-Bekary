# Идеи для масштабирования приложения

Список задумок на будущее — не в работе прямо сейчас, фиксируем, чтобы не забыть.

## 1. Раскрывающийся список товаров (группы, категории)
В экране менеджера (заказ на витрину) список товаров сделать сворачиваемым по категориям —
аккордеон вместо (или в дополнение к) плоского списка/вкладок-фильтров. Актуально, когда
товаров становится много и плоский список неудобно листать.

## 2. Автоматическое напоминание о дедлайне подачи заявки
Дедлайн 10:30 сейчас просто отображается в шапке — напоминание отстающим точкам шлёт вручную
управляющий кнопкой «Напомнить отстающим». Механизм push-уведомлений в Телеграм уже есть
(сделан для заявок на регистрацию, `src/lib/telegramNotify.ts`) — можно повесить
автоматическую задачу (Vercel Cron) рядом с дедлайном, которая сама разошлёт push всем точкам
без поданной заявки, без участия человека.

## 3. Реальная Telegram-идентификация для Управляющего/Территориального/Менеджера
Сейчас так по-настоящему устроен только вход Владельца (проверка подписи Telegram `initData`).
Управляющий — общий ПИН, территориальный — выбор из списка, менеджер — просто устройство
(localStorage). Правильное решение — распространить тот же механизм verifyTelegramInitData
на остальные роли, с привязкой Telegram id к записи в `staff`.

## 4. Довести права территориального управляющего до реального действия
Матрица прав (Владелец → «Роли и права») уже хранит, что разрешено территориальному
управляющему, но `TerritorialManagerView.tsx` сегодня полностью read-only — там нет ни одной
кнопки действия, чтобы это применить. Нужно прокинуть нужные обработчики (принять/отклонить
заявку, напоминания и т.д.) в этот экран и показывать их по матрице прав.

## 5. «Заказать как в прошлый раз»
Раз история заявок точки теперь есть (`order_history`), можно добавить кнопку в один клик на
экране менеджера — скопировать состав последней поданной заявки в черновик. Многие точки,
вероятно, заказывают +/- одно и то же изо дня в день.

## 6. Понятная ошибка при сбое отправки заявки
Сейчас если запрос на сервер не дойдёт (сеть, обрыв), менеджер об этом не узнает — ошибка
только в консоли браузера, на экране всё выглядит как обычно. Нужно показывать явное
сообщение об ошибке с кнопкой «Повторить отправку».

## 7. Отдельная тестовая база Supabase для локальной разработки
Локальный `npm run dev` сейчас использует ту же боевую базу, что и продакшн. 13.09.2026 это
обошлось дорого: фоновая проверка «исчезла ли операция `simulate-all`» раз в 10 секунд слала
POST на боевой сайт, пока не доехал деплой, — и каждый такой вызов заполнял все 27 точек
поддельными поданными заявками. Данные тогда не потерялись только потому, что в тот час
реальных заявок не было; утром это стёрло бы рабочий день всей сети. Всё поддельное удалено,
но причина осталась: одна база на разработку и на продакшн.

## 8. Табель сотрудников + личный кабинет внутреннего сотрудника — ✅ в основном сделано 14.09.2026
Сделано:
- Таблица `shifts` (одна смена на человека в день) и поле `staff.shift_rate`. Ставка
  копируется в смену и замораживается, чтобы повышение не переписывало прошлые месяцы.
- Плитка **«Табель»** в «Управление цехом» с двумя режимами: «по дню» (основной ввод) и
  «по сотруднику» (просмотр и правка месяца).
- Кабинет внутреннего сотрудника: сколько смен отработал и сколько заработал, список дней
  со ставками. Роль `employee` добавлена в `UserRole`, устройство теперь запоминает, чья
  это запись (раньше не запоминало и сотрудник попадал на экран заказа витрины).
- Переключатель «Цех / Сотрудник» в шапке у Владельца, чтобы посмотреть любой кабинет.

**Осталось из этой идеи:** сотрудник пока не видит свой чек-лист по цеху — только табель.
Вести табель может только Владелец, потому что роль «Управляющий» недостижима (см. №3).

## 9. Заявка на аванс на основе табеля
Продолжение идеи №8: сотрудник на основе своего табеля видит, сколько уже заработал, и может
подать заявку на аванс — с полями номер телефона Kaspi и сумма. Управляющему в «Управление
цехом» — новая плитка **«Запросы на аванс»** со списком поданных заявок (одобрить/отклонить,
как с заявками на регистрацию).

## 10. Дашборды на основе API iiko
Начать интеграцию с API iiko (Айко) — раздел с дашбордами, подтянутыми оттуда, с сравнением
периодов: вчера / прошлая неделя / прошлый год. Нужно будет выяснить, какие именно данные
доступны через API iiko и что конкретно сравнивать (выручка, списания, продажи по товарам и т.д.).

## 11. Красивые ТКК с картинками слоёв продукта
Технологическая карта блюда сейчас — просто таблица (название/количество/цена). Сделать
визуальное представление в стиле реальных ТКК — с картинкой в разрезе, показывающей слои
состава (как физически собирается блюдо), а не только текстовый список ингредиентов.

## 12. Клик по продукту у внутреннего сотрудника открывает его ТКК
Кабинет внутреннего сотрудника теперь есть (см. №8), но чек-листа в нём пока нет — сначала
нужно показать сотруднику его цеховой чек-лист, и уже оттуда при нажатии на блюдо открывать
техкарту (состав, технология), чтобы можно было свериться с рецептурой на месте, не отвлекая
управляющего.

## 13. Приёмка на точке
Сейчас в системе есть только «что заказали» — что реально доехало до точки, нигде не
фиксируется. Менеджер после доставки отмечает фактически принятое количество, и расхождение
«заказано → принято» сразу видно управляющему: это либо недовоз из цеха, либо потери по
дороге, и сегодня ни то, ни другое не отслеживается никак.

Экран переиспользуется почти целиком — тот же список товаров, что и в заявке, но со второй
колонкой факта. В базе нужно место под принятое количество (отдельное поле на строке заказа
либо отдельная сущность приёмки с привязкой к дате и точке).

Это первый из трёх шагов, замыкающих круг «заказ → производство → чек-лист → **приёмка** →
остатки и списания → норма на завтра». Без него следующие два повисают в воздухе.

## 14. Журнал действий
Сегодня нельзя ответить на вопрос «кто удалил эту заявку и когда» — никаких следов не
остаётся вообще. Нужна простая таблица «кто, что, когда, над чем»: приём и отклонение
заявок, удаление заявок, одобрение регистраций, правки каталога и цен.

Особенно нужен после того, как появятся права по должностям: без журнала выданные права
невозможно проверить — видно только то, что кнопка есть или её нет, но не то, кто чем
воспользовался.

## 15. Комментарий к заявке
Поле для заметки у заявки **уже есть в базе** (`notes` в таблице `orders` и в типе
`ShopOrder`), но в интерфейсе его нет нигде — ни при подаче, ни в реестре у управляющего.
«Завтра мероприятие, нужно больше обычного» сейчас передать некуда, кроме звонка.

Самый дешёвый пункт из всего списка: нужно только поле ввода на экране заявки и показ этого
текста в реестре.

## 16. Оповещения управляющим производством
Разослать решение по заявке (принята/отклонена) умеет всем троим — подавшему, владельцу и
управляющим производством. Но список получателей для последних (`ADMIN_NOTIFY_TELEGRAM_IDS`)
**пустой**, поэтому им не приходит ничего: ни о новых заявках на регистрацию, ни о решениях
по заявкам точек.

Это не задача на код — нужно добавить их Telegram-номера в настройки на сервере (и локально,
и в Vercel). Пока они не заданы, уже написанная половина работы по оповещениям простаивает.
