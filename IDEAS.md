# Идеи для масштабирования приложения

Список задумок на будущее — не в работе прямо сейчас, фиксируем, чтобы не забыть.

## 1. Раскрывающийся список товаров (группы, категории)
В экране менеджера (заказ на витрину) список товаров сделать сворачиваемым по категориям —
аккордеон вместо (или в дополнение к) плоского списка/вкладок-фильтров. Актуально, когда
товаров становится много и плоский список неудобно листать.

## 2. Автоматическое напоминание о дедлайне подачи заявки
Дедлайн 10:30 сейчас просто отображается в шапке — напоминание отстающим точкам шлёт вручную
управляющий кнопкой «Напомнить отстающим». Механизм push-уведомлений в Телеграм уже есть
(сделан для заявок на регистрацию, `src/lib/telegramNotify.ts`) — можно повесить
автоматическую задачу (Vercel Cron) рядом с дедлайном, которая сама разошлёт push всем точкам
без поданной заявки, без участия человека.

## 3. Реальная Telegram-идентификация для Управляющего/Территориального/Менеджера
Сейчас так по-настоящему устроен только вход Владельца (проверка подписи Telegram `initData`).
Управляющий — общий ПИН, территориальный — выбор из списка, менеджер — просто устройство
(localStorage). Правильное решение — распространить тот же механизм verifyTelegramInitData
на остальные роли, с привязкой Telegram id к записи в `staff`.

## 4. Довести права территориального управляющего до реального действия
Матрица прав (Владелец → «Роли и права») уже хранит, что разрешено территориальному
управляющему, но `TerritorialManagerView.tsx` сегодня полностью read-only — там нет ни одной
кнопки действия, чтобы это применить. Нужно прокинуть нужные обработчики (принять/отклонить
заявку, напоминания и т.д.) в этот экран и показывать их по матрице прав.

## 5. «Заказать как в прошлый раз»
Раз история заявок точки теперь есть (`order_history`), можно добавить кнопку в один клик на
экране менеджера — скопировать состав последней поданной заявки в черновик. Многие точки,
вероятно, заказывают +/- одно и то же изо дня в день.

## 6. Понятная ошибка при сбое отправки заявки
Сейчас если запрос на сервер не дойдёт (сеть, обрыв), менеджер об этом не узнает — ошибка
только в консоли браузера, на экране всё выглядит как обычно. Нужно показывать явное
сообщение об ошибке с кнопкой «Повторить отправку».

## 7. Отдельная тестовая база Supabase для локальной разработки
Локальный `npm run dev` сейчас использует ту же боевую базу, что и продакшн — уже как минимум
раз это привело к тому, что тестовые данные попали в реальные заявки точек №1 и №2. Обсуждали
и откладывали «до случая, когда понадобится» — при текущей частоте изменений схемы БД, кажется,
случай настал.

## 8. Табель сотрудников + личный кабинет внутреннего сотрудника
Сейчас роль «Внутренний сотрудник» (`employee` в `StaffRole`) существует только как запись в
списке персонала — своего экрана в приложении у неё нет вообще. Нужно:
- Отдельное окно для внутреннего сотрудника (свой вход, видит только своё): их чек-лист по
  цеху и табель — сколько дней отработали, сколько заработали.
- Учёт отработанных дней/смен нужно будет вести где-то в базе (новая сущность — записи табеля
  по сотруднику и дате), плюс ставка/расчёт заработка.
- В блоке Управляющего, в разделе «Управление цехом», — новая плитка **«Табель»** для
  просмотра и редактирования табеля по всем сотрудникам.

## 9. Заявка на аванс на основе табеля
Продолжение идеи №8: сотрудник на основе своего табеля видит, сколько уже заработал, и может
подать заявку на аванс — с полями номер телефона Kaspi и сумма. Управляющему в «Управление
цехом» — новая плитка **«Запросы на аванс»** со списком поданных заявок (одобрить/отклонить,
как с заявками на регистрацию).

## 10. Дашборды на основе API iiko
Начать интеграцию с API iiko (Айко) — раздел с дашбордами, подтянутыми оттуда, с сравнением
периодов: вчера / прошлая неделя / прошлый год. Нужно будет выяснить, какие именно данные
доступны через API iiko и что конкретно сравнивать (выручка, списания, продажи по товарам и т.д.).
